## 为什么做这一件事

赛题 1 的答疑写得很清楚（`赛题1-答疑-2026-10-21.md` Q6）：

> 赛题 1 要求参赛团队使用**华为云 CodeArts 码道代码智能体进行开发**……
> **仅使用其他 AI 编程工具，或仅使用华为云服务但未按要求使用 CodeArts 码道，则不符合赛题要求。**

当前还差四件（按严重度）：

| 缺口 | 性质 | 现状 |
|---|---|---|
| 云上真部署（RDS MySQL + Redis + ECS + 在线 Demo） | 资格线 / 复现红线 | 一次没跑过 |
| 华为云 MaaS 真端点 | 资格线 | `cloud` 只在本机 Ollama 上验过机制 |
| CodeArts 使用记录 | 风险 | T1–T3 是 CodeArts；T4–T9 由 Claude 完成 |
| 初赛材料 + 真机矩阵 | 必要项 | 另行安排 |

**本规格只做前两件，并顺带把第三件的记录做实。** 材料与真机不在本规格范围内。
T1–T9 的历史**不改写、不补录**——从本规格开始，在 CodeArts 里做的每一步如实记录。

## 完成定义（DoD）

以下每一条都要有可重跑的命令或可打开的证据，不接受“应该可以”：

1. 公网可访问的在线 Demo：`http://<EIP>/` 能打开，六个页面可用，手机宽度不溢出。
   ※ PWA 的**安装与离线**需要安全上下文（HTTPS 或 localhost）；纯 HTTP 下不作为已验收项，
   见 D8.0。不要在没有 HTTPS 的情况下宣称“可安装/可离线已验收”。
2. `GET /api/health` 返回 **200**，且 `database.backend = "mysql"`、`cache.backend = "redis"`、`degraded = false`。
3. `scheduler` / `watcher` 两个服务在 `docker compose ps` 里是 `healthy`，心跳文件在 10 分钟内更新过。
4. `python -m yechao cloud` 对**真实 MaaS 端点**跑通一次：发出的是脱敏后的条目，拿回了摘要；`data/cloud-lines.json` 有当天的记录。
5. `python -m yechao cloud --dry-run` 的输出能证明出网边界：没有 `actor` / `actor_account` / 群名，姓名名单比对数为正。
6. README 里的云部署步骤，换一台干净机器照着敲能复现；所有密钥不在仓库、截图、日志里。
7. 每个任务在 CodeArts 里完成，会话导出后与提交一一对应；材料里能如实说出哪一段是谁做的。

## 执行纪律

1. **所有代码与配置改动在 CodeArts 里做。** Claude 只做监督、验收和记录，不代写 CodeArts 的产出。
2. **一个任务一次提交**；提交信息写清这一任务做了什么；按路径 `git add`，不要 `git add -A`。
3. **失败要响。** 不静默回退 SQLite、不静默跳过 RDS/Redis、不静默把“没接通”写成“已部署”。占位或未完成必须显式报错并停下。
4. **密钥只走环境变量。** 不进配置文件、不进 README、不进提交、不进截图、不进会话导出。出现一次即停止任务并清理。
5. **先 `--plan-only`，再 apply。** 部署脚本真正 apply 的那一刻就在烧云资源；计划没看懂就不 apply。
6. **不改业务逻辑。** 允许改的只有部署契约（D1）。`domain/`、`application/`、持久化、数据源、业务路由一律不动；确有缺陷时另开任务卡，先写测试再修。
7. **不制造“看起来像成功”的状态。** 健康检查 200 但后端不是 MySQL/Redis，算未完成；日志里有 `batch_failed` 却没人看，算未完成。

## 前置决策（D2 之前必须定下）

| 项 | 默认 | 说明 |
|---|---|---|
| 区域 | `cn-north-4`（北京四） | 以账号实际有配额、有资源的区域为准；RDS/DCS/ECS 必须在**同一个 VPC** |
| 网络 | 复用已有 VPC/子网 | 没有默认 VPC 就先建一个；不要等 auto-deploy 自己建 VPC 后再找 RDS 放哪 |
| 公网端口 | `80` | 被策略挡住时用 `8080`，并在 README 写实际端口 |
| ECS 规格 | 8C16G（`s6.2xlarge.2`） | 跑 8B 级本地模型时的下限；预算不足见下方“模型放哪儿” |
| 访问来源 | Demo 对公网开放 | `--public-cidr 0.0.0.0/0`；SSH 只放行操作者公网 IP `/32` |
| HTTPS / PWA | 默认只保证 HTTP 网页 | PWA 安装与离线需要安全上下文；没有 HTTPS 就如实缩小验收范围（D8.0） |
| 预算 | 以代金券额度为上限 | 开通前在控制台确认计费方式与价格；演示结束按 D10 处理 |

### 模型放哪儿（先定，别到部署时才发现）

产品的主张是“敏感原文在本机完成抽取，只有脱敏后的条目离开这台机器”。
云端有两种放法，**默认选 A，B 只作为预算不足时的降级**：

**A. ECS 上跑本地模型（推荐，保住主张）**
- 原文在 ECS 内完成抽取，原文不出这台机器。
- MaaS 只用于 `[cloud]` 二次处理，输入是已脱敏的结构化条目。
- 需要 8C16G（8B 级模型）或 4C8G（4B 级模型）；模型文件约占 5–9 GB 磁盘。
- 演示环境用按量计费，演示结束停机或销毁。

**B. `[llm]` 也指向 MaaS（降级，必须如实说明）**
- 便宜、快、不用装模型；但**原文会离开 ECS**，与产品主张冲突。
- 只在预算/时间不足以支撑 A 时使用，并在 README、答辩材料、演示讲解里明确写：
  “云端演示版为降低资源门槛，抽取走 MaaS；本机三步复现仍保持原文不出机。”
- **不能**把 B 说成“本地预处理”。

无论 A/B，**MaaS 都用于 `[cloud]`**——这是赛题要的华为云大模型能力，也是本项目出网边界最干净的落点。

## D0 — 本地预演（不花云资源）

**目标**：在动云资源之前，把能在本机发现的错全部发现。

**动作**
1. 确认基线：
   ```bash
   git status --short          # 必须干净
   git tag --points-at HEAD    # 应包含 mobile-pwa
   git switch -c feat/cloud-deploy
   ```
2. 跑全量测试与部署契约：
   ```bash
   python -m pytest -q
   python -m pytest tests/contracts/test_deploy_contract.py -q
   ```
3. 用一份临时 env 校验 compose 插值（不启动容器）：
   ```bash
   cp .env.example .env.preflight
   docker compose --env-file .env.preflight -f deploy/docker-compose.yml config > /tmp/compose-rendered.yml
   ```

   ```bash
   docker compose --env-file .env.preflight -f deploy/docker-compose.yml build
   ```
   构建失败就在这里修，别带上云。

**验收**
- 全量测试绿；部署契约绿；`compose config` 成功；镜像构建成功。
- 删除 `.env.preflight`（它含示例值，不要留）。

**停止条件**：任一步失败，停下修；不带着红去申请云资源。

## D1 — 部署契约补齐（代码任务）

**目标**：让云端要用的三项能力在仓库里有正式入口，而不是靠 SSH 上去手改文件。

### 为什么需要这一张卡

- `[cloud]` 的 `base_url` / `model` 只从 `config/settings.toml` 读（`bootstrap._read_cloud`），
  而容器里的 `entrypoint.sh` 目前只把 `[llm]` 从环境变量写进去。云上若靠手改，
  换一台机器就复现不了。
- `YECHAO_CLOUD_API_KEY` 目前没有从 compose 传进容器。`cloud` 命令在容器里跑时拿不到 key。
- `.env.cloud` 不在 `.gitignore` 的 `.env` 规则里（`.env` 是精确匹配），**有被提交的风险**。
- Linux 上容器访问宿主 Ollama 没有 `host.docker.internal`；补 `host-gateway` 后，
  本地（Docker Desktop）与 ECS（Docker Engine）用同一个 base_url。

### 改动文件与要求

**1. `.gitignore`**
- 增加凭据类 env 的忽略规则，至少覆盖 `.env.cloud`：
  ```gitignore
  .env.*
  !.env.example
  ```
- 验收：`git check-ignore -v .env.cloud` 有输出；`git check-ignore -v .env.example` 没有输出。

**2. `.env.example`**
- 增加三个**可空**变量（写空值行，保证契约测试能读到）：
  ```bash
  YECHAO_CLOUD_BASE_URL=
  YECHAO_CLOUD_MODEL=
  YECHAO_CLOUD_API_KEY=
  ```
- 注释写清：`[cloud]` 只看脱敏后的条目；key 只在环境变量里。

**3. `deploy/docker-compose.yml`**
- 只给 `yechao` 服务增加：
  ```yaml
  YECHAO_CLOUD_BASE_URL: "${YECHAO_CLOUD_BASE_URL:-}"
  YECHAO_CLOUD_MODEL: "${YECHAO_CLOUD_MODEL:-}"
  YECHAO_CLOUD_API_KEY: "${YECHAO_CLOUD_API_KEY:-}"
  ```
- 三个服务（`yechao` / `scheduler` / `watcher`）增加：
  ```yaml
  extra_hosts:
    - "host.docker.internal:host-gateway"
  ```
  理由：模型端点在宿主的 Ollama 上，容器要能按名字找到宿主；否则 Linux 上只能写死私有 IP，
  而私有 IP 每次重建都会变。
- 不把 `YECHAO_CLOUD_API_KEY` 传给 `scheduler` / `watcher`：它们不调用 MaaS，少传一个少一个泄漏面。

**4. `deploy/entrypoint.sh`**
- 在写 `[llm]` 的那段逻辑旁边，增加 `[cloud]` 的重写：
  - 仅当 `YECHAO_CLOUD_BASE_URL` 非空时执行；
  - 只重建 `[cloud]` 段的 `base_url` / `model`，段内其它键（如 `enable_thinking`）原样保留；
  - **绝不**把 `YECHAO_CLOUD_API_KEY` 写进任何文件。
- 沿用现有 `[llm]` 那段的做法（按段走，不做全文 `sed`），避免“删掉别的段的同名键”那个旧坑。
- 保持 LF 行尾；`tests/contracts/test_deploy_contract.py` 已有一条 CRLF 判据。

**5. `tests/contracts/test_deploy_contract.py`**
- 增加一条文本判据：`entrypoint.sh` 里**不出现** `YECHAO_CLOUD_API_KEY`。
  理由：这条断言防的是“为了省事把 key 写进配置文件”——它不会报错，只会悄悄泄漏。
- 现有的反向判据（`.env.example` 里有、compose 里没有 ⇒ 失败）会强制上面第 2、3 步一起改，不要绕过它。

**验收**
```bash
python -m pytest tests/contracts/test_deploy_contract.py -q
python -m pytest -q
git check-ignore -v .env.cloud
```
- 契约测试绿；全量测试绿；`.env.cloud` 被忽略；`entrypoint.sh` 无 CRLF。

**提交**：`部署契约：云端口令注入、host-gateway 与 env 忽略规则`

**停止条件**：契约测试需要靠删断言才能过 ⇒ 停下，说明是哪条判据与设计冲突，不要改判据来迁就。

## D2 — 账号与资源预检（不花钱）

**目标**：把“账号没实名 / 没配额 / 没代金券 / AK 没配”这类问题在开通前发现。

**动作**
1. 华为云账号完成实名认证；确认目标区域可创建 ECS / EIP / 安全组 / KPS keypair。
2. 确认代金券或余额足以覆盖：ECS（按量）+ RDS + DCS + EIP + 流量。记录额度与有效期（不记录券码到仓库）。
3. 配置 AK/SK 到**当前终端环境**（不写文件）：
   ```bash
   export HW_ACCESS_KEY="..."
   export HW_SECRET_KEY="..."
   ```
4. 用 auto-deploy 的自检确认凭证被识别：
   ```bash
   python scripts/env_utils.py      # 返回 True
   python scripts/self_check.py
   ```
5. 确认本机（或 CodeArts 终端）具备：Python 3.10+、Bash、Terraform 1.8.0+、Git 2.0+、SSH/SCP。
6. 记录：账号名（脱敏）、区域、VPC/子网 ID、代金券额度与有效期。

**验收**
- `env_utils.py` 返回 `True`；`terraform version` ≥ 1.8.0；区域配额够。
- 预检结论写进 `docs/云部署记录.md`（D9 建），不写敏感值。

**停止条件**：实名/配额/代金券任一不满足 ⇒ 停下，先解决账号问题，不要用“试试能不能开”的方式探配额。

## D3 — VPC、RDS MySQL、DCS Redis 开通（优先用 CodeArts Skills）

**目标**：把赛题要求的“关联开通 RDS、Redis”在 CodeArts 里做成，而不是只在控制台点几下。

**动作**
1. 确认 VPC 与子网（复用或新建）：
   - 记录 `vpc-id`、`subnet-id`、网段（例如 `192.168.1.0/24`）。
   - ECS 稍后会落在这个子网里。
2. **优先在 CodeArts 里用华为云 Skills 开通**：
   - 用自然语言描述规格，要求返回实例 ID、内网地址、端口、VPC/子网。
   - 建议规格（以控制台实际可选项为准）：
     - RDS for MySQL **8.0**，2C4G 或最低可用规格，存储 40 GB，端口 3306，同 VPC/子网。
     - DCS Redis **5.0/6.0/7.0**，1 GB 单机，端口 6379，同 VPC/子网，**开启密码**。
3. Skills 失败时回退控制台开通，但**如实记录失败原因**（材料里不能把控制台开通说成 Skills 开通）。
4. 建库与账号（在 RDS 控制台 SQL 窗口或同 VPC 的临时 ECS 上执行）：
   ```sql
   CREATE DATABASE yechao CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   CREATE USER 'yechao'@'%' IDENTIFIED BY '<强密码>';
   GRANT ALL PRIVILEGES ON yechao.* TO 'yechao'@'%';
   FLUSH PRIVILEGES;
   ```
   - 密码里的 `@` `:` `/` 写进连接串时要做 URL 编码（`%40` `%3A` `%2F`）。
   - 表**不要手工建**，由程序首次启动时 `CREATE TABLE IF NOT EXISTS`。
5. 白名单：
   - RDS：先把子网网段加入白名单（临时），D5 拿到 ECS 私网 IP 后收窄到该 IP。
   - DCS：同样先加子网网段，D5 后收窄。
   - 不给公网访问；测试若临时开过公网，测完立刻关闭。
6. 连通性验证（同 VPC 的临时 ECS 或 AI Shell）。
   ※ 不要把密码拼进命令行：它会留在 shell 历史与进程列表里。用环境变量传：
   ```bash
   export RDS_PASSWORD='<密码>'
   export REDIS_PASSWORD='<密码>'
   python - <<'PY'
   import os
   import pymysql
   import redis

   pymysql.connect(
       host="<RDS内网地址>", user="yechao",
       password=os.environ["RDS_PASSWORD"], database="yechao",
       connect_timeout=5,
   ).close()
   print("mysql ok")

   c = redis.Redis(
       host="<DCS内网地址>", port=6379, password=os.environ["REDIS_PASSWORD"],
       socket_timeout=5,
   )
   print("redis", c.ping())
   PY
   unset RDS_PASSWORD REDIS_PASSWORD
   ```

**验收**
- 两条连通性命令都成功；RDS/DCS 与未来 ECS 在同一 VPC。
- 记录实例 ID、内网地址、端口、白名单变更（不记录密码）。

**停止条件**：RDS/DCS 与 ECS 不在同一 VPC、或白名单无法覆盖 ECS 子网 ⇒ 停下重开或调整网络，不要部署一个连不上库的 ECS。

## D4 — 部署计划（`--plan-only` 闸门，绝不 apply）

**目标**：在烧钱之前，确认 auto-deploy 真的看懂了这份仓库。

### 为什么必须有这个闸门

auto-deploy 的 Compose 路径要求仓库里有它认得的 Compose 文件。本仓库的 compose 在
`deploy/docker-compose.yml`，不是根目录。它可能识别，也可能只看到根目录没有而退到别的路径。
**猜错的代价是：只部署了 `yechao` 一个服务，scheduler/watcher 没起来，而页面看起来是好的。**

**动作**
1. 安装 Skill（在 CodeArts 里用自然语言）：
   ```text
   帮我安装 auto-deploy skill，Skill 地址是：https://gitcode.com/weixin_43883336/auto-deploy
   ```
   确认目录里有 `SKILL.md`、`scripts/`、`templates/`、`README.md`。
2. 准备 `.env.cloud`（**不提交**，D1 已保证被忽略）：
   - `YECHAO_PORT=80`
   - `YECHAO_DATA_DIR=/app/data`
   - `YECHAO_CONFIG_DIR=/app/config`
   - `YECHAO_DB_URL=mysql://yechao:<URL编码密码>@<RDS内网地址>:3306/yechao`
   - `YECHAO_REDIS_URL=redis://:<密码>@<DCS内网地址>:6379/0`
   - `YECHAO_LLM_BASE_URL=http://host.docker.internal:11434/v1/chat/completions`
   - `YECHAO_LLM_MODEL=<ECS 上实际 pull 的模型 tag>`
   - `YECHAO_API_KEY=`（本地 Ollama 不需要）
   - `YECHAO_DAILY_AT=07:30`
   - `YECHAO_WATCH_INTERVAL=600`
   - `YECHAO_WATCH_SOURCES=`（空 = 合成语料；演示阶段足够）
   - `YECHAO_CLOUD_BASE_URL=<MaaS 控制台复制的完整 chat/completions 地址>`
   - `YECHAO_CLOUD_MODEL=<MaaS 控制台的模型名>`
   - `YECHAO_CLOUD_API_KEY=<MaaS key>`
3. 跑计划：
   ```bash
   python scripts/auto_deploy.py --repo D:/github/yechao --app-name yechao \
     --region cn-north-4 \
     --network-mode reuse --existing-vpc-id <vpc-id> --existing-subnet-id <subnet-id> \
     --flavor s6.2xlarge.2 --app-port 80 --public-cidr 0.0.0.0/0 \
     --ssh-cidr <操作者公网IP>/32 \
     --env-file .env.cloud --plan-only
   ```
4. **逐项读产物，不只看退出码**：
   - `.auto-deploy/analysis.json`：部署方式是不是 `docker-compose`？
   - `.auto-deploy/deployment-plan.md`：
     - 是否包含 `yechao` / `scheduler` / `watcher`（`redis` 本地服务可以起来但不使用）？
     - 端口映射是否为 80 → 8000？
     - 环境变量注入方式是什么？`--env-file` 落到哪个路径？
     - SSH 来源是否被收窄到操作者 IP？
   - 如果计划只部署 `yechao`：**停止**。不要“先部署主服务再说”。

**验收**
- 计划产物明确回答上面四个问题，且部署方式是 Compose、服务齐全。
- 计划文件与 `analysis.json` 存档（D9 放进证据目录；其中不含密码）。

**停止条件**
- 未识别到 `deploy/docker-compose.yml`；
- 只识别到单服务；
- `--env-file` 的落点无法确认；
- 端口/SSH 来源与预期不符。

以上任一发生，停下报告，由监督方决定是补根目录 compose（`include:` 或等价做法）还是调整调用方式。
**不要在 CodeArts 里自行发明第二份 compose 来“让它能跑”。**

## D5 — ECS 部署（apply）

**目标**：一台 ECS 上起四件事：应用、scheduler、watcher、本机 Redis（后者闲置，缓存走 DCS）。

**动作**
1. 计划确认无误后，去掉 `--plan-only` 重跑同一条命令，加 `--yes`：
   ```bash
   python scripts/auto_deploy.py --repo D:/github/yechao --app-name yechao \
     --region cn-north-4 \
     --network-mode reuse --existing-vpc-id <vpc-id> --existing-subnet-id <subnet-id> \
     --flavor s6.2xlarge.2 --app-port 80 --public-cidr 0.0.0.0/0 \
     --ssh-cidr <操作者公网IP>/32 \
     --env-file .env.cloud --yes
   ```
2. 记录：ECS 实例 ID、EIP、私网 IP、仓库上传路径、Compose 工作目录。
3. 把 RDS / DCS 白名单从“子网网段”收窄到 **ECS 私网 IP**。
4. 首次健康检查：
   ```bash
   curl -i http://<EIP>/api/health
   ```
   期望：HTTP 200，响应体里 `database.backend = "mysql"`、`cache.backend = "redis"`、`degraded = false`。
5. 容器状态与日志：
   ```bash
   docker compose ps
   docker compose logs --tail=120 yechao
   docker compose logs --tail=80 scheduler
   docker compose logs --tail=80 watcher
   ```

### 第一次真跑 MySQL 的风险（必须正视）

`mysql_store.py` 的方言形状是**静态验证**过的，没对着真 MySQL 跑过。第一次启动可能出现：

- `CREATE TABLE IF NOT EXISTS` 的列类型 / 索引 / FULLTEXT 语法不被 MySQL 8.0 接受；
- 占位符、UPSERT、自增回填在真库上的行为与假连接不同；
- `utf8mb4` 排序规则与代码里的比较假设不一致。

**处置**：任何 SQL 错误 ⇒ **停止**，把完整错误（SQL 语句 + MySQL 报错）贴进报告，另开任务卡修，
先补一条能复现的测试，再改实现。**不允许**为了“先跑起来”把 `YECHAO_DB_URL` 改回 SQLite。

**验收**
- 四个容器 `Up`；`yechao` 为 `healthy`；scheduler/watcher 心跳新鲜。
- `/api/health` 三项全对。
- 日志里没有反复出现的 SQL / 连接 / 认证错误。

**停止条件**
- 健康检查 503 且错误指向 MySQL；
- 健康检查 200 但 `database.backend` 不是 `mysql`（说明连接串没生效）；
- `cache.backend` 不是 `redis`（说明 DCS 没接通，或还连着本地 redis）；
- 容器反复重启；SSH 连不上且 `--ssh-cidr` 已确认。

### D6.2 播种

**为什么先停两个循环**：`demo` / `refine` / `digest` 都是写者；watcher 也在跑同一组命令。
写者锁会让其中一方让路，症状是“命令跑了一半就退出”，而不是报错。

```bash
docker compose stop watcher scheduler
docker compose exec yechao python -m yechao demo
docker compose exec yechao python -m yechao refine
docker compose exec yechao python -m yechao digest
docker compose start watcher scheduler
```

**逐条看输出，不只看退出码**：
- `demo`：消息条数、预筛保留/丢弃；
- `refine`：处理条数、失败条数；`batch_failed` 必须被解释，不能略过；
- `digest`：生成了哪几天的日报、多少条、模型写/机械行各多少。

### D6.3 页面验收

- 打开 `http://<EIP>/`：日报页应显示合成语料的最后一天，有内容。
- 信息流、日历、配置、隐私、类目、状态六个页面都能打开，控制台零 error。
- 375 宽度无横向溢出；触控目标 ≥44px。
- 离线标注与 Service Worker 只在 HTTPS 或 localhost 下验收；HTTP 下只验页面与控制台，
  并把这一条作为已知边界写进记录（见 D8.0）。
- `python -m yechao metrics` 的数字要么是真实数字，要么明确显示“无法计算（分母为 0）”。

**验收**
- `demo` / `refine` / `digest` 三步退出码 0（`refine` 有可解释的失败时按实际情况记录）；
- 日报页有内容；六个页面可用；
- scheduler/watcher 重启后心跳新鲜，日志里能看到“读的是合成语料”的显式提示。

**停止条件**：`refine` 连不上模型、或整批失败且原因是端点/模型名/鉴权 ⇒ 先修端点；
不要用“机械行兜底”掩盖抽取没跑成。

## D7 — MaaS 真端点切换与验证

**目标**：把 `[cloud]` 从“本机 Ollama 验过机制”变成“真实 MaaS 跑通”。

**动作**
1. 在华为云控制台开通 MaaS 模型服务（以控制台实际界面为准）：
   - 进入 MaaS / 在线推理，开通目标模型；
   - 复制 **完整** 的 OpenAI 兼容地址（要包含 `/v1/chat/completions` 这一段）；
   - 记录模型名；
   - 创建 API Key。
2. 更新 ECS 上的部署 env（`.env.cloud` 或 auto-deploy 落下的那份），填入：
   - `YECHAO_CLOUD_BASE_URL`
   - `YECHAO_CLOUD_MODEL`
   - `YECHAO_CLOUD_API_KEY`
3. 重启应用让 entrypoint 写入 `[cloud]`：
   ```bash
   docker compose up -d yechao
   ```
4. 确认配置文件里**只有地址与模型名，没有 key**：
   ```bash
   docker compose exec yechao sh -c 'grep -A3 "^\[cloud\]" /app/config/settings.toml'
   ```
5. 端点最小连通测试（不发任何业务数据，只证明地址/模型/key 三者对得上）：
   ```bash
   docker compose exec yechao python - <<'PY'
   import json, os, urllib.request, urllib.error
   url = os.environ["YECHAO_CLOUD_BASE_URL"]
   body = json.dumps({
       "model": os.environ["YECHAO_CLOUD_MODEL"],
       "messages": [{"role": "user", "content": "ping"}],
       "max_tokens": 8,
   }).encode()
   req = urllib.request.Request(url, data=body, headers={
       "Content-Type": "application/json",
       "Authorization": "Bearer " + os.environ["YECHAO_CLOUD_API_KEY"],
   })
   try:
       with urllib.request.urlopen(req, timeout=30) as r:
           print("HTTP", r.status)
   except urllib.error.HTTPError as e:
       print("HTTP", e.code, e.read()[:500].decode("utf-8", "replace"))
   PY
   ```
   - 401：key 不对；404：地址或模型名不对；超时：网络/区域/安全组。
6. 出网边界先看后发：
   ```bash
   docker compose exec yechao python -m yechao cloud --dry-run
   ```
   验收点：
   - 打印的是**完整的**将要发送的内容，不是一句“将发送 N 条”；
   - 没有 `actor`、`actor_account`、群名；
   - 姓名名单比对数 > 0（为 0 表示名单空，姓名这一维**没查**）。
7. 真发一次：
   ```bash
   docker compose exec yechao python -m yechao cloud
   ```
   期望：`发出 N 条`、`拿到 M 行摘要`；失败批次要逐条看原因，不能只看最后一行。
8. 落盘与审计：
   ```bash
   docker compose exec yechao sh -c 'ls -l /app/data/cloud-lines.json && head -c 500 /app/data/cloud-lines.json'
   ```
   再跑一次 `digest`，确认日报用上了云端摘要（模型写的行或类目修正可见）。

**验收**
- 最小连通测试 `HTTP 200`；
- `cloud --dry-run` 的输出满足上面三条边界；
- `cloud` 真实返回摘要，`cloud-lines.json` 有当天内容；
- 配置文件里没有 key；仓库、日志、截图里也没有。

**停止条件**
- MaaS 侧 401/404/超时，重试一次仍失败 ⇒ 停下，记录完整错误；
- 只能靠把 key 写进配置文件才能跑通 ⇒ 停下，这是设计问题，不是部署技巧；
- dry-run 里出现人名/号码/群名 ⇒ 立即停止，先修脱敏，不要发。

## D8 — 在线 Demo 验收（公网 + 手机）

### D8.0 HTTPS 与 PWA 的边界（先读，别把不能验收的写成已验收）

Service Worker 与 PWA 安装要求**安全上下文**：HTTPS 或 localhost。纯 `http://<EIP>/` 下：

因此：
- **主线**：在线 Demo 按 HTTP 验收“网页可用”；PWA 安装/离线按 localhost 三步复现验收，
  材料里分两栏写，不混成一句“云端 PWA 已验收”。
- **要在线演示 PWA**：需要 HTTPS。可选路径：
  1. 域名 + 证书（大陆区域通常涉及备案，周期长，先确认时间）；

  3. 从 ECS 起一个 HTTPS 隧道（临时演示可用，但依赖第三方、地址不稳定，不能作为唯一路径）。
- 无论走哪条，**HTTPS 地址与证书来源要写进 README**；自签证书导致的浏览器警告要如实说明，
  不能截图时绕过警告却宣称“正常”。

**动作**
1. 用**手机蜂窝网络**（不是 ECS 本地、不是同一 Wi-Fi）打开 `http://<EIP>/`。
2. 逐项验收（HTTP 范围）：
   - 日报首屏有内容；六个页面可切换；
   - 375 / 390 宽度无横向溢出；触控目标 ≥44px；
   - 控制台零 error；`navigator.serviceWorker` 不存在时页面不报错、不白屏；
   - 写操作失败时可见，不静默。
3. PWA 范围（仅 HTTPS 或 localhost）：
   - 浏览器出现安装入口；
   - 离线打开时显示“缓存于 HH:MM”；
   - 写操作在离线时失败可见。
4. 服务端验收：
   ```bash
   curl -fsS http://<EIP>/api/health
   docker compose ps
   docker compose logs --since=30m | grep -iE "error|traceback|failed" | head -50
   ```
   - 心跳文件 mtime 在 10 分钟内；
   - `docker compose ps` 无反复重启。
5. 记录演示环境信息：区域、规格、模型放法（A/B）、端口、访问地址、开始时间、预计停机时间。

**验收**
- 公网手机可访问；六页可用；HTTP 范围内控制台零 error；
- PWA 安装与离线标注**在 HTTPS 或 localhost 下**真实可见；HTTP 下如实写“未验收”；

**停止条件**

- 手机端溢出或触控不达标 ⇒ 回到移动端任务卡修，不在部署层掩盖；

## 附录 A：环境变量清单

只列**键名与用途**，不写值。

| 变量 | 必填 | 本地 | 云上（A/B） | 谁读 |
|---|---|---|---|---|
| `YECHAO_PORT` | 是 | 宿主端口 | `80` | compose |
| `YECHAO_DATA_DIR` | 是 | 容器内数据目录 | `/app/data` | compose / scripts |
| `YECHAO_CONFIG_DIR` | 是 | 容器内配置目录 | `/app/config` | compose / scripts |
| `YECHAO_DB_URL` | 是 | `sqlite:///...` | `mysql://...`（RDS） | bootstrap |
| `YECHAO_REDIS_URL` | 是 | `redis://redis:6379/0` | `redis://:...@...`（DCS） | bootstrap |
| `YECHAO_LLM_BASE_URL` | 是 | 本机 Ollama | A：`host.docker.internal`；B：MaaS 地址 | entrypoint → `[llm]` |
| `YECHAO_LLM_MODEL` | 是 | 本地模型 tag | A：ECS 模型 tag；B：MaaS 模型名 | entrypoint → `[llm]` |
| `YECHAO_API_KEY` | 否 | 本地可空 | A 可空；B 填 MaaS key | bootstrap |
| `YECHAO_CLOUD_BASE_URL` | 否 | 可空 | MaaS 完整地址 | entrypoint → `[cloud]` |
| `YECHAO_CLOUD_MODEL` | 否 | 可空 | MaaS 模型名 | entrypoint → `[cloud]` |
| `YECHAO_CLOUD_API_KEY` | 否 | 可空 | MaaS key | bootstrap |
| `YECHAO_DAILY_AT` | 否 | `07:30` | `07:30` | scheduler |
| `YECHAO_WATCH_INTERVAL` | 否 | `600` | `600` | watcher |
| `YECHAO_WATCH_SOURCES` | 否 | 空（合成语料） | 演示阶段空 | watcher |

`YECHAO_CLOUD_*` 三项是 D1 新增的契约；在 D1 完成前，`.env.example` 里没有它们，compose 也不会传。
