# 夜抄 · Nocturnal Notes

把散在多个来源（群聊、会议转写、邮件、网页通知）里的消息，整理成一份按天可读的日报。
敏感原文在本机完成抽取，只有脱敏后的结构化结果离开这台机器。

「多个来源」是**设计**不是现状：取数抽成一个 `MessageSource` 端口，**归一化的责任在源自己**
（会议转写要切段、邮件是自洽短文本切了反而拆散）。现在实现了哪些源、哪些还只是留了位置，
见下面的「数据来源」一节。

## 三步复现

※ 先把配置模板复制一份（见下节「第一次运行」）。

```bash
python -m yechao demo      # 离线建库，不需密钥
python -m yechao refine    # 本地模型抽取（需要 OpenAI 兼容端点）
python -m yechao digest    # 生成日报
python -m yechao serve     # 网页打开
```

`demo` 不联网、不需要任何密钥：它**走源层**取仓库自带的合成语料（见 `ingest`）、建库、
生成默认配置与群清单快照，并把预筛「保留多少、丢弃多少、为什么」打印出来。
`serve` 默认打开 <http://127.0.0.1:9000>，端口被占用时会自动往上找一个，并把实际地址打印出来。

### 第二步（`refine`）需要一个模型端点

`demo` 与 `serve` 都不需要模型；**`refine` 需要**，而且它**没有离线兜底** ——
没配端点时它会拒绝跑并说清缺什么。这一步刻意不静默跳过：跳过的话你会拿到一份
「今天群里很安静」口吻的结果，而真相是根本没抽。

最短的一条路（本地、免费、原文不出这台机器）：

```bash
ollama serve                 # 另开一个终端（首次安装见 https://ollama.com/）
ollama pull qwen3:14b        # ① 评委机器上：**任何一个**模型都行，这一行只是举例
                             # ② 本队部署用的是 `yechao-llm`（本机那份 bonsai-2:27b，
                             #    是自己建的，公共库里 pull 不到）
```

然后把 `config/settings.toml` 里这两行取消注释（模板里它们本来就是写好的）：

```toml
[llm]
base_url = "http://127.0.0.1:11434/v1/chat/completions"
model = "yechao-llm"        # 填你实际 pull 下来的那个（本队部署 = yechao-llm）
```

※ **任何 OpenAI 兼容端点都可以**，不限于 Ollama —— 把 `base_url` 与 `model`
换成你那一家的即可。密钥走环境变量 `YECHAO_API_KEY`，**不写进配置文件**
（配置文件会被导出、会被提交）。

※ 模型选多大的：8B 级能把三步复现跑完（实测）。更大更稳，但首次加载与每批
推理都更慢；**换模型只改 `model` 这一行**。

※ `digest` **不需要**模型：模型不可用时它会退化成机械行 —— 条目照样在，
只是一句话的措辞不是模型写的，而且报告里看得出来。

### 从别的来源取数

```bash
python -m yechao ingest                  # 默认源（合成语料）
python -m yechao ingest --source web     # 换一个源
```

名字不认识时会**报错并列出可用的源**，退出码 2。

`ingest` 是**取数的入口**：`demo` 只是它的一种用法（走合成源、顺便建库）。
源按**名字**选，名字不认识就报错并列出可用的源 —— **不回落**到默认源，
因为回落的症状是「用户以为读的是真源，其实读的是合成语料」，而报告一切正常。

### 第一次运行：先建配置

`config/` **不入库** —— 它是运行期产物，会被用户改（加群、改类目、填端点）。
仓库里给的是一份**模板**：

```bash
cp -r config.example config      # Windows PowerShell: Copy-Item -Recurse config.example config
```

※ 别把 `config/` 提交进来 —— 下一个人 clone 下来会带着**别人的**群与端点，
而那看起来像「默认配置」，排查方向完全错。

CLI 还提供 `ingest`、`ledger`、`export`、`metrics`、`doctor`、`cloud`，`python -m yechao --help` 可看完整用法。

`ledger` 是查账用的：每一次 `refine` / `ingest` / `digest` 都会把「这一轮跑了什么、哪一条消息为什么没进条目」落进库（`runs` / `run_entries`），`python -m yechao ledger --msg <id>` 就是用来回答那后半个问题的。

## 依赖

- Python ≥ 3.11（使用了标准库 `tomllib`）。
- `pip install -e .`；或手动 `pip install fastapi uvicorn`。
- 开发测试：`pip install -e ".[dev]"`（pytest、httpx）。
- **模型端点**（`refine` 需要，见上面「第二步」）：任何 OpenAI 兼容端点都行；
  本地 [Ollama](https://ollama.com/) 是最省事的一条路。`digest` 没有它也能跑（退化成机械行）。

**不装 Node 也能看网页。** `serve` 服务的是仓库里已构建的 `web/dist/`，不是前端源码。若 `web/dist/` 不存在，`serve` 会明确返回 501 并提示构建方式，而不是静默给一个 404。

## 模型怎么配

端点和模型名写在 `config/settings.toml` 的 `[llm]` 段；**密钥不写进配置文件**，走环境变量 `YECHAO_API_KEY`（配置文件会被导出、被提交，密钥不能跟着走）。

```toml
[llm]
base_url = "http://127.0.0.1:11434/v1/chat/completions"
model = "bonsai-2:27b"
# enable_thinking = false
```

`base_url` 要写完整的 `chat/completions` 地址。`enable_thinking` 是**三态**：

- 不写这个键 = 请求里不发该字段（通用 OpenAI 端点最安全）；
- `false` / `true` = 显式发送该值。

本地 Ollama 的最小流程：

```bash
ollama serve
ollama pull bonsai-2:27b
python -m yechao refine
```

没有配端点时，`refine` 会以非零退出码结束，并打印该改哪个文件、写什么键；它不会猜一个默认地址。网页仍可打开；模型不可用时，`digest` 会用机械行兜底并在输出里说明。

## 部署与后端

默认是**单机 / SQLite / 无缓存**，什么都不用配（三步复现就是这样）。上云换成
MySQL（RDS）与 Redis，**只在环境变量里配** —— 连接串里有密码，而配置文件会被导出、
会被提交：

```bash
YECHAO_DB_URL=mysql://user:pass@host:3306/yechao
YECHAO_REDIS_URL=redis://host:6379/0
```

| 项 | 本机默认 | 云上 |
|---|---|---|
| 存储 | SQLite 文件 | MySQL / RDS（**同一个仓储端口的另一个实现**） |
| 缓存 | **空实现**，且**可观测**：`backend=none`、`enabled=false`、命中率是 `null`（不是 `0`） | Redis / DCS；连不上时 **fail open**，但记 `errors` 与 `last_error` |

※ **配了连接串却连不上会报错，不会回落成 SQLite。** 回落的症状是「用户以为写进了
云数据库，其实写在本机文件里」—— 而那看起来是成功的。

※ **诚实说明**：MySQL 与 Redis 两个实现**没有在本机对着真库跑过**（本机没有
MySQL / Redis 服务）。验证方式是静态的：用假连接把 `MySQLStore` 的每个端口方法
真的跑一遍、逐条核方言形状（占位符、自增回填、UPSERT、FULLTEXT 取舍…）。
**它证明的是方言形状对，不是 MySQL 的解析器一定接受这些语句。** 这句话也写在
`mysql_store.py` 的 docstring 里。

`GET /api/health` 回答三件事 —— 服务 / 库 / 缓存：

- **库挂了 ⇒ 503**：每条路由都要读库，回 200 就是把「坏」说成「健康」
- **缓存挂了 ⇒ 200 + `degraded: true`**：产品完整可用（只是慢），算成不健康会让
  编排层反复重启一个本来就正常的容器 —— 而重启修不好 Redis

`deploy/docker-compose.yml` 的 healthcheck 探的就是它。

## 架构

四层，依赖方向只有一个：**外 → 内**。

```
interfaces/      HTTP 路由、CLI              ← 只做输入输出
application/     用例编排、端口定义（Protocol）  ← 只依赖 domain 与自己定义的端口
infrastructure/  SQLite、模型客户端、配置      ← 实现端口
domain/          纯逻辑，零 I/O                ← 不依赖任何外层
bootstrap.py     组合根（唯一横跨多层的地方）
```

分层护栏在 `tests/contracts/test_layering.py`：白名单式的 import 判据、领域层无 I/O、无导入环，并带空转自检（每层必须有实际被判的文件，避免「扫描空集合的断言恒为真」）。

## 日报里的事怎么分类

**判据是「这条消息要读者做什么」，不是「它属于哪个话题」。**

读者打开日报，问的是「我要做什么」，不是「这条属于哪一类内容」。所以六个类目
就是这句话的六种答案：

| slug | 名称 | 读者要做什么 |
|---|---|---|
| `todo` | 要办的事 | 在某个时间之前**办完**一件手续 |
| `attend` | 要到场的事 | 在某个时刻**出现在某地** |
| `know` | 只要知道 | **不用动手**，但要知道一个安排 |
| `claim` | 失物招领 | 去**核对、归还或认领**一件物品 |
| `trade` | 转让求购 | 去**联系**卖方或买方 |
| `recruit` | 招人 | 去**投递或应聘** |

按话题分（学业 / 活动 / 生活…）有个**已知的歧义**：「讲座通知：请于周五前报名」
既是「活动」（讲座）又是「学业」（报名），两个都说得通 —— 于是同一条消息在不同
批次里可能被判成不同的类目。按「要读者做什么」判，它就是 `todo`（去报名，有截止），
歧义消失。

类目的 `desc` 是**判据**、会**逐字拼进提示词**，而且**用户可以在网页上改**
（`config/categories.toml`）。所以提示词不是常量，是一个函数 —— 加一个类目，
模型自动就认它。

## 两条不变量

1. **网页侧不得写入主库。** 接口层的 GET 一律使用只读连接（`mode=ro` 加 `PRAGMA query_only`），由 SQLite 本身拒绝写操作，而不是靠代码自觉。测试会用只读连接真的发一条 INSERT 并断言抛异常。
2. **删除是软的。** 删除只置标记，`items` 的行与 `item_sources` 的来源引用都还在；去重依据的 `covered_msg_ids()` 连被软删条目的来源一起返回，所以这些消息仍算「已处理」，设计上不会被下一轮抽取复活。撤销依赖 append-only 的编辑事件，事件里保存「原来是什么」。

## 数据来源

### 现在实现了哪些源

| 源 | 状态 | 从哪儿读 |
|---|---|---|
| `synth` 合成语料 | √ 实现 | `demo` 走的就是它（离线、不需密钥） |
| `web` 网页通知 | √ 实现 | 三种入口：URL（先读 `robots.txt`）/ 带侧车的**离线夹具** / 本地 HTML |
| `mail` 邮件 | √ 实现 | 两种入口：`.eml` / `.mbox` 文件；**IMAP 只读**直连信箱 |
| `meeting` 会议转写 | √ 实现 | 腾讯会议 / 钉钉的导出目录；也自动探测本机客户端的会议历史库 |
| `video` 视频 | √ 实现 | 本地字幕（`.srt` / `.vtt`）；视频页链接（含 B 站） |
| `subscription` 订阅 | √ 实现 | 小红书 / 抖音 / 快手 / 微博 / 知网（先读 `robots.txt`，登录态与协议两道闸） |
| `qq` 本机 QQ 群消息 | √ 实现 | **零操作**：读本机 QQ 的加密消息库（钥匙从已登录的 QQ 进程内存里取）；也认同形的 `.db` 夹具与导出文件 |

※ **每个源的目标都要能被指定**，没有一个默认读到别处去。`synth` 之外的源都
不在 `DEFAULT_SOURCES` 里 —— 不给 `--source` 时只读合成语料，而报告里会打出
实际用到的源名（「我明明想读会议转写，怎么读的是合成语料」一眼可见）。

※ **没配目标的源不会静默回落到合成语料。** 回落的症状是「用户以为读的是真源，
其实读的是假数据」，而报告一切正常 —— 那正是这个项目最防的形状。

### QQ 源：本机那条路，与离线那条路

```bash
# 零操作：读本机 QQ 的群消息（QQ 开着并登录着就行）
python -m yechao ingest --source qq

# 评委路径：一份同形的合成库，不需要装 QQ
python -m yechao ingest --source qq \
  --config-dir config \
  # 或者直接点名那份夹具
YECHAO_QQ_SOURCE=yechao/infrastructure/sources/fixtures/qq-group-msg.db \
  python -m yechao ingest --source qq
```

本机那条路的形状（实测，Windows，QQ NT 9.9.31.49738）：QQ 把群消息写在
`<数据根>/<QQ号>/nt_qq/nt_db/nt_msg.db`，那是一个 **SQLCipher 库**，
前面套了 1024 字节明文外壳。钥匙**不在文件里** —— 库里只有一段账号级标识，
真正的钥匙是登录时向服务器换的，只存在于**正在运行的 QQ 进程内存**里。
所以这个源会去读那块内存（只读：`PROCESS_VM_READ`，不注入、不调试、不写），
取不到就**响亮报错**，而不是返回一个空列表 —— 「读不到」与「群里今天很安静」
在日报上是同一句话，那是这个项目最防的形状。

⚠️ 因此：**它只在 Windows 上成立**，而且要求 QQ 开着。评委机器上没有 QQ 时走
上面那份夹具 —— 两条路读的是**同一套列名与同一个解析器**（夹具是按真库的形状
造的），所以夹具跑通了，真库那条路的解析也就被验过了。

### 网页源的离线夹具

`yechao/infrastructure/sources/fixtures/qingwu-notices.html` 是一份**手写**的合成
通知页面（假校名「青梧」、假域名 `notice.example.test`），旁边一个同名侧车
`.meta.json` 记着它的来源与指纹（指纹对不上 = 夹具被改过而侧车没重生成）。

```bash
YECHAO_WEB_SOURCE=yechao/infrastructure/sources/fixtures/qingwu-notices.html \
  python -m yechao ingest --source web
```

它存在的理由：**评委不在你那个校内网。** 没有夹具，网页源的演示不可复现。
夹具存的是**原始 HTML**、不是解析结果 —— 解析器改进了，旧夹具还能重放；
存解析结果的话，解析器一变夹具就废，又得联网。

### 合成语料

演示数据是 `yechao/domain/synth.py` 里的**合成语料**：群名一律挂在虚构校名「青梧」下，号码、姓名、群号全部自己编造（手机号 `1770000100X`、群号 `82000000X`），格式对即可，不含任何真实群、真实姓名或真实消息。

这份语料同时是**唯一能给出真值的评测集**——每条消息都带一个 `Expect`（该不该保留、该判成什么类目、截止日/开始时刻的原文、应被脱敏的号码与姓名等）。真实数据没有真值，隐私原因下也无法人工标注，所以 `metrics` 的所有准确率只对这份合成语料成立。

## 可量化指标

```bash
python -m yechao metrics
```

输出形如：

```
夜抄 · 端到端指标（对合成语料的真值）

以下是**模型那一侧**的数字（读库里 refine 真的落下的条目）：
  类目正确率                    <命中>/<分母> = <百分比>
  截止日抽取召回                ...
  开始时刻抽取召回              ...
  幻觉率（字段无依据的比例）    ...
  脱敏召回（该抹的抹了）        ...
  脱敏误伤（抹多了）            ...

口径说明（这几项都会造出「假缺陷」，所以写在这里）：
  · 覆盖率的分母是**该送进模型的**，未处理的不算进模型指标的分母
  · 开始时刻的分母**不含**「源文只给了相对时间」的那些（结构上填不进）
  · 幻觉率的分母是**所有被检查过的字段**，不只是有产出的条目
```

口径：

- **覆盖率单列**：分母是「该送进模型的」条数，分子是「真的送了的」。预算耗尽、批失败、取消而未处理的，不会被算成「模型漏了」。
- **判据不适用不进任何分母**：例如源文只给「明早」这种相对时间，`start_ts` 那一格结构上就填不进；把它算作漏抽会造出一个假缺陷。被排除的条数会单独报出来。
- **幻觉率的分母是所有被检查过的字段**，不只是「产出了条目的那些」——否则漏抽越多、分母越小，幻觉率反而越好看。
- 分母为 0 时输出「无法计算（分母为 0）」，不是 0%——「没测」不能冒充「一次都没命中」。

类目、截止日、开始时刻、幻觉这四项读的是库里 `refine` **真的落下**的条目，所以要先跑 `refine`；没跑过时它们显示「无法计算（分母为 0）」，工具不会编一个数字。

## 几条不该被误解的事

- **隐私边界证明的是「出网文本不含已知名单里的姓名」**，不是「不含任何姓名」。姓名脱敏是对配置中已知昵称（及其剥出的人名本体）做精确子串替换；模型若自己补出一个不在名单上的名字，这条替换拦不住。这是已知边界，不应当被简化成「无隐私风险」。同理，隐私页的 `clean` 只表示审计记录里没有命中，不等于「没有隐私风险」。
- **模型挂了，日报不会空。** 模型调用失败、输出解析不出、回连不上的行被丢弃时，每条条目都有机械行兜底（`标题 · 地点 · 群名`）。CLI 会明确打印「模型这次没跑成」和「上面那条是用机械行兜底的」，日报统计里也会写「以下为机械整理」——「今天没有日报」与「今天模型没跑成」是两句不同的话。
- **`demo` 重跑什么都不覆盖。** 已存在的 `groups.toml` / `categories.toml` 保留不动；库里的消息按 `msg_id` 幂等写入，已有条目、软删状态与人工编辑一条都不动。想要干净重来，用 `python -m yechao demo --fresh`（这是**唯一**会删库的路径，且只删这个库）。
